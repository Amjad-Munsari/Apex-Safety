## 1. System Classification

**System Type:** Content Generation (Structured Drafting & Extraction)

**Description:**
Takes raw on-site Fire Risk Assessment (FRA) data (text, photos, speech-to-text transcripts) and transforms it into a professional, branded PDF report. It drafts the content into a structured format suitable for the `@react-pdf/renderer` engine. "Good" looks like a comprehensive, technically accurate report that requires minimal to no editing by Matt before he approves it for the client.

**Critical Failure Modes:**
1. **Hallucination of Hazards:** Inventing fire risks or mitigation requirements that were not in the raw assessment data.
2. **Omission of Critical Findings:** Failing to include high-priority hazards recorded on-site.
3. **Schema Violation:** Returning unstructured text instead of the strict JSON format required by the PDF renderer.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Fire Safety & Compliance

**User Population:** Solo practitioner (Matt Dineen) reviewing reports before sending to commercial/residential property clients.

**Stakes Level:** High (Legal compliance and life safety implications).

**Output Consequence:** Reports dictate client spending on safety mitigations and serve as legal proof of compliance. Inaccuracies create liability for the practice or unaddressed life-safety risks for the client.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|---|---|---|---|---|
| Technical Accuracy | Hazards precisely match field notes/photos. | Mentions "sprinklers" when none exist. | Critical | FRA Standards |
| Tone & Professionalism | Objective, clear, regulatory language. | Conversational, ambiguous, or alarmist. | Medium | Brand Guidelines |
| Completeness | Every room/area assessed has a corresponding status. | Missing an entire floor from the summary. | High | FRA Standards |

### Known Failure Modes in This Domain

- **Generic Boilerplate Overload:** LLMs tend to output generic fire safety advice instead of specific, actionable mitigations based on the actual site data.
- **Severity Misclassification:** Misinterpreting a minor compliance issue as a critical immediate-action hazard.

### Regulatory / Compliance Context

Reports must comply with the Regulatory Reform (Fire Safety) Order 2005 (UK). The AI is assisting a competent person (Matt), not acting as one. The "Review & Approve" gate is legally necessary.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| Competent Fire Assessor (Matt) | Final review of every generated report before PDF rendering. Rubric calibration. |

## 2. Framework Decision

**Selected Framework:** Vercel AI SDK Core (`ai` package) with Zod for structured outputs.

**Version:** `^3.x` (latest)

**Rationale:**
Since the entire application is built on Next.js App Router and Server Actions, the Vercel AI SDK is the native, most lightweight choice. It provides out-of-the-box `generateObject` which pairs perfectly with Zod schemas to guarantee the structured JSON needed for the PDF renderer. It avoids the bloat of LangChain or LlamaIndex which are unnecessary for a straightforward drafting pipeline.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain | Overkill for a simple extraction/drafting pipeline; adds unnecessary abstractions. |
| Raw OpenAI SDK | Lacks the cross-provider flexibility and unified streaming/object generation hooks of Vercel AI SDK. |
| n8n | Explicitly ruled out by Phase 7 Context constraints (must be local to Next.js). |

**Vendor Lock-In Accepted:** Partial. We are locked into Vercel AI SDK, but we can easily swap model providers (e.g., OpenAI to Anthropic) by changing the provider string.

## 3. Framework Quick Reference

### Installation
```bash
npm install ai @ai-sdk/openai zod
```

### Core Imports
```typescript
import { generateObject } from "ai";
import { createOpenAI } from "@ai-sdk/openai";
import { z } from "zod";
```

### Entry Point Pattern
```typescript
const openai = createOpenAI({
  apiKey: process.env.OPENROUTER_API_KEY,
  baseURL: "https://openrouter.ai/api/v1",
});

const result = await generateObject({
  model: openai("openai/gpt-4o-mini"),
  schema: reportSchema,
  prompt: `Draft a report based on these notes: ${rawData}`,
});
```

### Common Pitfalls
1. Failing to handle `generateObject` schema validation errors gracefully (it throws if the LLM fails to match the Zod schema).
2. Context window limits if dumping raw base64 images into the prompt without resizing.

## 4. Implementation Guidance

**Model Configuration:**
- Model: `openai/gpt-4o-mini` via OpenRouter (or direct OpenAI depending on env).
- Temperature: `0.1` (We want deterministic, factual extraction, not creative writing).

**Core Pattern:**
Server Action `draftReport(assessmentId)` fetches the raw data from Supabase, calls `generateObject` with the predefined `ReportSchema` (Zod), and saves the resulting JSON to a `draft_report` column for Matt to review.

**Tool Use:**
No tools needed. Pure data transformation.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic/Zod

```typescript
// Zod schema enforces the exact structure the PDF renderer expects
const reportSchema = z.object({
  executiveSummary: z.string(),
  hazards: z.array(z.object({
    location: z.string(),
    description: z.string(),
    severity: z.enum(["Low", "Medium", "High", "Critical"]),
    recommendedAction: z.string(),
  })),
  complianceStatus: z.enum(["Pass", "Action Required", "Fail"]),
});
```

### Prompt Engineering Discipline
- **System Prompt:** Define the persona ("You are an expert UK Fire Risk Assessor drafting an official report...").
- **Instructions:** Explicitly forbid hallucination ("Do not invent hazards not present in the input data").

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| Schema Adherence | Pass/Fail | Code (Zod validation) | Critical |
| Hazard Precision | 1-5 (No invented data) | LLM Judge (Self-reflection) | High |
| Formatting | Pass/Fail | Code (PDF rendering success) | Medium |

### Eval Tooling

**Primary Tool:** Manual "Human in the Loop" (Matt's Review Gate) for v1.

**Setup:**
The application already includes a "Review & Approve" UI. Matt serves as the primary evaluator for every generated report.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Schema Validation | LLM output doesn't match Zod | Retry automatically up to 2 times, then escalate to user with error state. |
| Empty Input | Assessment has no data | Block generation, require user to add notes first. |
