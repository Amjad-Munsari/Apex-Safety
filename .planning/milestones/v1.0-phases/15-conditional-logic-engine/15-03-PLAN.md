    buildDependencyMap(schema):
    - Iterate every entity. For each rule in `entity.attributes.visibilityRules.rules ?? []`, add `direct[r.sourceEntityId].add(entityId)`.
    - For each computedField entity, read `entity.attributes.computedInputs` (an object map per the existing attribute factory); add `computedInputs[entityId].add(inputEntityId)` for every input value that is a non-empty string.
    - Edge semantics: `X → Y` means "a change to X requires re-eval of Y". Direct: source → consumer. Computed: input → computedField.
    resolveScope(schema, entityId):
    - Walk parents (via the inverse of `children` arrays). Return "root" when entity is not a child of any container; return `repeatingSection.id` when the nearest ancestor container is a repeatingSection; return `sectionGroup.id` when nearest ancestor is a sectionGroup.
    - Build a parent-map cache on first call (per-call closure is fine — schema is small).
    isAncestorScope(schema, consumerId, sourceId):
    - True when sourceId's scope is one of consumerId's ancestor scopes (root counts as everyone's ancestor).
    - Returns true when both are root.
    - Returns false when both are inside DIFFERENT repeatingSection instances of the same repeatingSection (this is the cross-instance case — D-03 rejects).
    - Returns false when consumer is root and source is inside any repeatingSection (root→inside-repeating REJECT per D-03).
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client save request → server `saveDraftAction` / `publishTemplateAction` | Schema JSON crosses; validateRuleGraph runs server-side before INSERT (wired in plan 15-05). |
| Client schema with hostile rule chains → renderer | Without cycle detection, a cyclic schema could (in a naive implementation) cause infinite re-evaluation. The shared shouldBeProcessed hook from plan 15-02 is non-recursive — bounded — but validateRuleGraph is the defensive layer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-03-01 | Denial of Service | Interpreter render loop | mitigate | validateRuleGraph rejects cyclic schemas at SAVE time (D-08); cycles never reach the renderer. Even if a hostile client tampers with `template_versions.schema_json` directly, the `shouldBeProcessed` hook from plan 15-02 is O(rules-on-this-entity) per call — no recursion — so worst-case behaviour is degraded responsiveness, not infinite loop. |
| T-15-03-02 | Tampering | Cross-template rule refs | mitigate | validateRuleGraph operates only within a single template's schema. A rule's `sourceEntityId` that names an entity in another template is treated as an orphan (`reason: "orphan-source"`, advisory) at save time and returns `false` at engine eval (per evaluateRule's unknown-key path from plan 15-02). No cross-template data path exists by construction. |
| T-15-03-03 | Information Disclosure | Cycle-error payload | mitigate | CycleError exposes entity LABELS and IDS only — no field values, no PII. JSON-serialisable Error message is safe to surface in the admin builder UI. |
| T-15-03-04 | Tampering | Cross-instance D-03 bypass | mitigate | `isAncestorScope` explicitly rejects two repeatingSection-child entities even when both belong to the same repeatingSection (different instances). validateRuleGraph emits `reason: "cross-instance"` and sets `ok: false`. Server-side enforcement means a client-side UI bypass cannot smuggle the rule into a published version. |
| T-15-03-05 | Repudiation | Save-time rejection | accept | Save rejection produces a JSON Error message; Next.js server-action telemetry already captures the throw via the existing error pipeline. No new audit surface required. |
</threat_model>
