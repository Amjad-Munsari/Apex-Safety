## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-06-01 | Tampering | UI scope filter (D-03) | mitigate | Source-field dropdown uses `isAncestorScope` from plan 15-03 to filter candidates; a hostile admin can't easily pick a cross-instance source. Server-side `validateRuleGraph` (plan 15-05) is the authoritative guard — UI filter is defence-in-depth, not the sole control. |
| T-15-06-02 | Tampering | UI action filter for computedField (A7) | mitigate | Action dropdown excludes `require` when host is computedField. Server-side: even if a `require` rule is smuggled onto a computedField (e.g., via direct API), `computeFormProgress` never includes computedField in the required set per `computed-field.ts` JSDoc, so the rule is a no-op. |
| T-15-06-03 | Spoofing | surface prop | accept | `surface` is purely visual — controls colour token selection. No security-relevant branching. AGENTS.md compliance is a UX / multi-tenancy contract, not a security boundary. |
| T-15-06-04 | Information Disclosure | Builder rule data | accept | Rules are stored in `template_versions.schema_json` already protected by template-version RLS from Phase 13. No new exposure surface. |
| T-15-06-05 | Tampering | onChange handler | mitigate | All writes go through the existing setAttr → builderStore.setEntityAttribute → coltorapps validateSchema path, which runs the visibilityRulesAttribute.validate (plan 15-01) on every change. Malformed shapes are rejected before they reach the store. |
