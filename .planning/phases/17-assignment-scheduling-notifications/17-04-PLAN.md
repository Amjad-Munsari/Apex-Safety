## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vercel cron → DB | Cron handler verifies `Authorization: Bearer ${CRON_SECRET}` before any DB write (T-17-AUTH gate). Service-role client bypasses RLS — appropriate for a cron, identical to Phase 5's expiry route. |
| Cron → n8n | sendAssignmentReminder ultimately calls dispatchNotification which posts to `N8N_WEBHOOK_URL` with the `X-Webhook-Secret` header. Same path Phase 5 already uses. No new env vars in this plan. |
| Submit action → generateNextOccurrence | Uses RLS-aware createClient (NOT service-role). The user calling the action is the assignment's owner — the SELECT/UPDATE on form_assignments hits the existing RLS policy that scopes to client_id. T-16-04 invariant: the SourceAssignment is constructed from a server-side SELECT, never from the user-supplied payload. |
| Inline trigger ↔ cron PASS B | Both paths use `recurrence_generated_at` as a serialization point. Race condition: if a submit completes at exactly 07:00 UTC and the cron starts the same second, both paths could try to generate. Mitigation: the column is set with `.update().eq("id", X)` — the second writer's UPDATE sees `recurrence_generated_at` already set (because the first writer's UPDATE landed); but the second writer would have ALREADY called generateNextOccurrence and inserted a successor row. Outcome: two successor rows for one completion. Acceptable for v1 — the race window is tiny (~1s once a day for ~7 clients) and the duplicate is detectable via a future SELECT GROUP BY completed_assignment_id (not present in v1, deferred). Documented in T-17-13 below. |
