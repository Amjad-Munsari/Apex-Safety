<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| coltorapps interpreter → shouldBeProcessed hook | The hook runs on every value change; misbehaviour can hang the UI. Hook is bounded — only iterates this entity's own rules. |
| submitted answers → stripHiddenAnswers (server) | Hostile client could submit values for fields that ought to be hidden. Strip is the defence. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-02-01 | Information Disclosure | answers_json | mitigate | `stripHiddenAnswers` strips every visible===false entity and recurses into repeatingSection instances. Plan 15-05 wires it server-side AFTER `validateEntitiesValues` so hostile client values for hidden fields never reach the DB nor the AI report prompt. |
| T-15-02-02 | Denial of Service | shouldBeProcessed hook | mitigate | Hook iterates only its host entity's rule list (bounded by rule count) and never calls evaluateVisibility (no full schema walk on every keystroke). Worst case O(rules-on-this-entity); even a 100-rule entity is microseconds. Cycle detection (plan 15-03) prevents construction of pathological rule sets at save time. |
| T-15-02-03 | Tampering | Hidden-required logic | mitigate | `cascadeVisibility` forces required=false whenever visible=false (D-07). evaluateVisibility composes this so neither the renderer nor the server scrub can be tricked into demanding a value for a hidden field. |
| T-15-02-04 | Repudiation | Hidden field strip | accept | Stripped values are not logged anywhere; the design intent (D-01) is "preserve on hide in store, drop on submit". A future audit trail could record what was stripped, but is out of scope. |
| T-15-02-05 | Spoofing | evaluateRule unknown operator | mitigate | `evaluateRule` returns false for unknown operators rather than throwing — matches Pitfall 3 (orphan source defensive). Combined with `visibilityRulesAttribute.validate` whitelist (plan 15-01), unknown operators cannot reach evaluateRule via the save path; the defensive return is for fuzz/replay safety. |
</threat_model>
